## 1. 目的

本書は、企画書で定めた方向性をもとに、NeedSeedで実現する機能・品質の要件と、各リリースの範囲を定める。

## 2. 用語集

| 用語 | 定義 |
| --- | --- |
| 企業 | 課題を登録する法人ユーザー。運営者がアカウントを発行する |
| 起業家or起業を考えている人 | 課題に応募し、事業として解決を目指す個人ユーザー。自分でアカウントを登録する |
| 運営者 | プラットフォームを管理するユーザー |
| 課題 | 企業が登録する、解決したい経営・業務上の問題 |
| 課題概要 | 課題のうち、全ユーザーに公開される情報 |
| 課題詳細 | 課題のうち、企業が承認した起業家or起業を考えている人にのみ公開される情報 |
| 応募 | 起業家or起業を考えている人が課題に対して解決の意思と提案を示すこと |
| マッチング | 企業が応募を承認し、両者がつながった状態 |
| ユーザーストーリー | どのような機能がなぜ必要かをわかりやすい言葉で簡潔に説明したもの |

## 3. 利用者と役割

| 利用者 | 主な役割 |
| --- | --- |
| 企業 | 課題の登録・管理、応募の承認・却下 |
| 起業家or起業を考えている人 | 課題の検索・閲覧、応募、応募状況の確認 |
| 運営者 | 企業アカウントの発行、ユーザーと課題の管理、不適切な利用への対応 |
| 未ログインユーザー | サービス概要と公開中の課題概要の閲覧 |

### 3.1 アプリ構成

利用者の立場ごとにアプリを分け、認証(ログイン状態)も立場ごとに分離する。企業と起業家は別のアカウント体系であり、同じ人が両方を利用する場合も、システム上は無関係の別アカウントとして扱う。

| アプリ | 対象 | ドメイン | 認証 |
| --- | --- | --- | --- |
| APP1 ポータル | 全員 | xxx.com | なし(立場を選んで各アプリへ進む) |
| APP2 企業アプリ | 企業 | company.xxx.com | Clerk(企業用) |
| APP3 起業家アプリ | 起業家or起業を考えている人 | founder.xxx.com | Clerk(起業家用) |
| APP4 運営アプリ | 運営者 | admin.xxx.com | Clerk(運営用) |

データベースは4アプリで共通(Supabase PostgreSQL 1プロジェクト)とする。

## 6. 非機能要件

### 6.1 性能
- 主要な画面は通常時2秒以内に表示されること
- 課題一覧はページネーションを行い、1ページあたり20件程度とする

### 6.2 セキュリティ
- 通信はすべてHTTPSで行う
- 認証はClerkを利用し、企業・起業家・運営者でアプリケーションを分離する(ログイン状態は共有しない)
- 企業アプリでは自己サインアップを無効化し、運営者が登録したアカウントのみログインできる
- 認可(誰が何をできるか)はアプリ層で行い、すべてのデータアクセスを共通の認可関数経由に限定する
- 認可ロジックは自動テストで検証する
- すべての入力値をサーバー側で検証する
- DBの接続情報はサーバー側のみで保持し、ブラウザには公開しない
- 企業アプリのセッションで起業家アプリ・運営アプリのAPIを呼べないこと(他の組み合わせも同様)
- 課題詳細や連絡先など、公開範囲が限られる情報を権限のない利用者に返さない

### 6.3 可用性・運用
- 無料枠(Vercel Hobby / Supabase Free / Clerk Free)の範囲で運用し、稼働率の保証は行わない
- 独自ドメインを取得して運用する(費用が発生する)
- エラーはログとして記録し、確認できるようにする
- デモデータはシード用スクリプトで再投入できるようにする

### 6.4 対応環境
- PC・スマートフォンの最新版ブラウザ(Chrome、Safari、Edge、Firefox)
- レスポンシブデザインに対応する

### 6.5 保守性
- 主要なロジックに自動テストを用意する
- mainへのマージ前にCIでテストを実行する
- モノレポ構成とし、DBアクセスや認可などの共通処理はパッケージとして共有する

## 7. スコープ外(今回は対応しない)

- 決済・契約機能
- 企業の実在確認・審査のシステム化(運営者による手動確認・登録で代替する)
- 企業と起業家のアカウント連携・統合
- 企業・起業家間でのログイン状態の共有(SSO)
- 多言語対応
- ネイティブアプリ
